# Как здесь работают агенты

Четыре условия автономной работы, каждое привязано к тому, что в этом репозитории реально
существует и что можно запустить. Документ описывает не намерения, а механику: у каждого
условия есть команда, артефакт и отказ, который оно печатает.

---

## 1. Доверие к артефакту, а не к слову: проверка в рантайме

**Отчёт агента — это гипотеза. Доказательство — запущенная система.**

Компиляция, линтер и модульные тесты не отвечают на вопрос «работает ли продукт». В этом
репозитории на него отвечают **десять e2e-сьютов**, которые собирают приложение, устанавливают
его, запускают и водят по **DevTools Protocol**: кликают, заполняют формы, читают PostgreSQL и
снимают экран. Это и есть «руки и глаза».

```bash
bash scripts/e2e-all.sh          # весь стек + все сьюта
node scripts/e2e-calendar.mjs    # один сьют
```

Что уже ловилось только так — и ни одним модульным тестом:

| Дефект | Как найден |
|---|---|
| PDF обрезался до одной страницы | сьют считает страницы файла |
| тёмная тема: белый текст на мятной кнопке (1.92:1) | измерение контраста на живом экране |
| поля форм белые с почти белым текстом | измерение **элемента**, а не текстового узла |
| полосы календаря вставали отдельной строкой | проверка вычисленного `grid-row` |
| стенд переигрывал записи | чтение лога самого приложения |

**Правило.** Утверждение без команды в выводе — не результат. Скриншот, лог, число — да.

## 2. Две петли управления

### Внутренняя петля — тот, кто пишет код

Пишет, запускает проверки, чинит. Инструмент — `scripts/check-all.sh` по рабочему дереву:
быстро, можно гонять сколько угодно.

```bash
bash scripts/check-all.sh          # без e2e
bash scripts/check-all.sh --e2e    # весь гейт
```

Внутренняя петля заканчивается, когда гейт зелёный **на коммите в ветке**, а не на рабочем
дереве.

### Внешняя петля — координация и независимый аудит

Координатор (Team Lead, «chief of staff») разбивает задачу и раздаёт её узким исполнителям.
Инженер не работает ручным прокси: у каждой задачи есть владелец, ожидаемая область записи и
критерий приёмки, а результат стекается в общий журнал.

Инструменты внешней петли:

```bash
scripts/verify-branch.sh <ref>     # независимая проверка коммита
scripts/merge-verified.sh <pr>     # слияние только с вердиктом
```

Правила, которые делают петли петлями, а не пожеланиями:

- **Исполнитель не проверяет себя.** Вердикт выдаёт тот, кто кода не писал.
- **Области записи не пересекаются.** Двое одновременно в одном файле — это не параллелизм,
  а потерянная правка.
- **Зависимости упорядочивают работу.** Проверка не начинается, пока не закончилась та, от
  которой она зависит.

## 3. Кодовая база как память агента

Контекст модели ограничен и деградирует. Поэтому **повторяющаяся ошибка переезжает в структуру
репозитория** — в тот же коммит, где её починили. Не в документ, который кто-то должен
вспомнить, а в проверку, которая падает.

Что уже так устроено:

| Ошибка | Чем стала |
|---|---|
| CSS-токен использован, но не определён | `tests/styles.test.cjs` |
| цвет записан литералом вне блоков токенов | `tests/styles.test.cjs` |
| модуль зовёт экспорт соседа без импорта | `tests/module-graph.test.cjs` |
| импорт имени, которого модуль не экспортирует | `tests/module-graph.test.cjs` |
| контракт клиента и сервера разошёлся | `fixtures/*.json` + тест на дрейф |
| коммит прямо в `main` | `.githooks/pre-commit` |
| цена считалась дважды по-разному | `src/domain/booking/pricing.cjs`, зеркало в Go |
| подсказка в интерфейсе без перевода | `tests/i18n.test.cjs` |

**Правило.** Починил — добавь проверку, которая поймала бы это. Если проверка уже есть и не
поймала — сначала почини проверку, потом код.

Хуки включаются один раз на клон:

```bash
bash scripts/install-hooks.sh      # git config core.hooksPath .githooks
```

Отдельно про линтеры и типы: в проекте **сознательно нет ни сборщика, ни линтера** — рендерер
это ES-модули, которые грузятся как есть. Роль строгих правил здесь играют тесты-стражи выше и
фикстуры; добавление TypeScript в готовый продукт — отдельное решение, а не побочный эффект
настройки агентов.

## 4. Автономное слияние через независимый аудит

**Тот, кто написал изменение, его не сливает.** Не потому что авторы небрежны, а потому что
автор не может быть удивлён собственной работой: он знает, какой тест упал бы, будь изменение
неверным, — поэтому запустил именно его.

Порядок:

```bash
# 1. Автор доводит ветку до зелёного гейта у себя
bash scripts/check-all.sh --e2e

# 2. Ветка уходит в PR
git push -u origin feature/<имя>
gh pr create --base main --head feature/<имя>

# 3. ПРОВЕРЯЮЩИЙ получает вердикт — в ЧИСТОЙ копии коммита
scripts/verify-branch.sh <sha>

# 4. Слияние, которое без вердикта не состоится
scripts/merge-verified.sh <pr-number>
```

Почему вердикт что-то значит:

- проверка идёт в **чистой копии** (`git worktree`), а не в дереве автора: неотправленные правки
  не могут пройти гейт за автора, а «у меня работает» перестаёт быть аргументом;
- вердикт привязан к **sha коммита**, и вердикт для другого sha не принимается — слияние
  отклоняется, если ветка уехала после проверки;
- вердикт — **файл** (`artifacts/verdict-<sha>.json` + `.md`), а не фраза в чате;
- **полный вердикт обязателен.** Быстрый (без e2e) принимается только с явным
  `RENTKEEPER_ALLOW_QUICK_VERDICT=1`: он прогоняет модульные сьюты и пропускает те, что запускают
  приложение, — то есть о поведении не говорит ничего.

Отказы, которые гейт печатает:

| Ситуация | Что скажет |
|---|---|
| вердикта нет | `для PR #N нет вердикта` + команда проверки |
| вердикт для другого sha | `ветка изменилась после проверки` |
| вердикт провален | `слияние запрещено` |
| стек уже запущен | `порт 8787 или 9555 занят` — двум проверкам не разойтись на одной машине |
| GitHub отдаёт устаревший head | `один из ответов устарел` — гейт сверяет ответ GitHub с `origin` и отказывает при расхождении |

**Почему гейт сверяет два источника.** Ответ GitHub об обновлении ветки отстаёт от пуша на
несколько секунд, и гейт на этом попался: он слил pull request по вердикту для коммита, который
уже не был вершиной ветки. Теперь положение ветки читается у `origin`, ответы сравниваются, и при
расхождении слияние останавливается: вердикт относится к конкретному коммиту, и «какой из двух
ответов верный» — не вопрос, который стоит решать слиянием.

CI на GitHub — вторая, независимая инстанция того же гейта: `scripts/check-all.sh` на ubuntu,
включая веб-сборку под xvfb. Локальный вердикт и CI друг друга не заменяют: первый отвечает
«что именно я проверил и когда», второй — «воспроизводится ли это на чистой машине».

## Что делать, когда что-то пошло не так

| Симптом | Действие |
|---|---|
| Гейт падает только у проверяющего | почти всегда состояние машины: `scripts/e2e-stack.sh down`, затем снова |
| Сьют падает «иногда» | это находка, а не флак. Воспроизведите, инструментируйте, запишите в `AGENTS.md` |
| Проверка не может запуститься | она обязана сказать `SKIP` и почему. Молчаливый пропуск — это ложный зелёный |
| Вердикт есть, но старый | он привязан к sha; после нового коммита проверяйте снова |
